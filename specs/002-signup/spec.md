# 기능 명세: 회원가입

**기능 브랜치**: `feature/signup`

**작성일**: 2026-08-05

**최종 수정일**: 2026-08-10

**상태**: 계획 준비 완료

**입력**: 기존 회원가입 명세를 공통 스타일, 공통 Loading과 데스크톱·태블릿·모바일 디자인에 맞게 갱신한다.

- [태블릿 회원가입 화면 1024px](https://www.figma.com/design/EQgddmgx1PAr79a4uyVyRf/%EC%A0%9C%EB%AA%A9-%EC%97%86%EC%9D%8C?node-id=16-3553)
- [모바일 회원가입 화면 480px](https://www.figma.com/design/EQgddmgx1PAr79a4uyVyRf/%EC%A0%9C%EB%AA%A9-%EC%97%86%EC%9D%8C?node-id=16-5073)
- 세 화면의 입력 항목 이름과 순서는 디자인 차이와 관계없이 `닉네임`, `이메일`, `비밀번호`, `비밀번호 확인`으로 통일한다.
- 태블릿과 모바일 디자인의 `이름` 표기는 `닉네임`으로 교체한다.
- 비밀번호는 기존 확정 요구사항인 영문·숫자·특수문자를 포함한 `8~16자`를 적용한다. Figma의 `8~10자` 안내 문구는 이 요구사항과 충돌하므로 `8~16자` 안내로 교체한다.
- 배치, 크기, 색상과 타이포그래피는 각 기준 화면의 Figma를 따른다. 기능 명세와 디자인의 문구 또는 동작이 다르면 이 명세를 우선한다.

## 의존 명세

- [공통 Header 명세](../001-common-header/Header.md)
- [공통 전체 화면 Loading 명세](../007-loading/spec.md)

- `/signup`의 Header는 `src/app/(site)/layout.js`에서 한 번 제공되며 회원가입 페이지가 직접 렌더링하지 않는다.
- `/signup` 최초 진입 시 Header는 접힌 상태여야 하며, 펼침·접힘과 사용자 상태 정책은 공통 Header 명세를 따른다.
- 회원가입 페이지 작업에서는 `Header.jsx`와 `src/app/(site)/layout.js`를 수정하지 않는다.

## 작업 범위와 책임

- 회원가입 페이지와 전용 스타일은 각각 `src/app/(site)/signup/page.js`, `src/app/(site)/signup/page.module.scss`에 대응한다.
- 입력란과 버튼의 공통 외형은 기존 `src/styles/abstracts/_mixins.scss`의 mixin을 재사용한다.
- 회원가입 페이지를 위해 Input 또는 Button 공통 React 컴포넌트를 새로 만들지 않는다.
- UI 우선 단계는 반응형 화면, 약관 선택, 입력 상태와 클라이언트에서 판단 가능한 검증 상태까지만 다룬다.
- 실제 Supabase 회원가입, 닉네임·이메일 중복 확인, API, 세션 저장, 이메일 인증과 성공 이동은 후속 인증 연동 범위다.
- UI 우선 단계에서는 가짜 회원가입 성공, 가짜 사용자, 가짜 중복 확인 결과 또는 테스트용 Promise를 만들지 않는다.
- 실제 회원가입 요청이 연결되면 요청을 소유한 화면이 Boolean `isLoading`으로 기존 Loading의 표시와 종료를 제어한다.
- 회원가입 이벤트 요청에는 Suspense fallback이나 Next.js `loading.js`를 사용하지 않는다.
- 실제 로그인 상태를 판정할 수 없는 UI 우선 단계에서는 로그인 사용자 접근용 CommonModal을 미리 연결하지 않는다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 가입 정보 작성 (우선순위: P1)

비로그인 사용자는 필수 약관에 동의하고 유효하며 사용 가능한 닉네임과 이메일, 안전한 비밀번호를 입력해 회원가입을 진행한다.

**우선순위 이유**: 신규 사용자가 서비스 계정을 만들기 위해 반드시 완료해야 하는 핵심 흐름이다.

**독립 검증**: 빈 화면에서 약관과 네 입력 항목을 순서대로 작성하며 각 검증 상태와 가입하기 버튼의 상태를 확인한다.

**인수 시나리오**:

1. **상황** 비로그인 사용자가 `/signup`에 처음 진입했을 때, **동작** 화면을 확인하면, **결과** 접힌 Header와 빈 약관·입력 상태, 비활성화된 가입하기 버튼이 표시된다.
2. **상황** 두 필수 약관에 동의하고 네 입력값의 필수·형식·일치 검증과 닉네임·이메일 중복 확인이 모두 통과했을 때, **동작** 화면 상태를 확인하면, **결과** 가입하기 버튼이 활성화된다.
3. **상황** 가입 가능한 상태일 때, **동작** 가입하기 버튼을 선택하면, **결과** 회원가입 요청은 한 번만 시작되고 화면 전체 Loading이 표시된다.
4. **상황** 회원가입 요청이 성공했을 때, **동작** 성공 처리가 완료되면, **결과** 회원가입 완료 화면(`/signup/complete`)으로 이동한다.
5. **상황** 회원가입 요청이 성공했을 때, **동작** 완료 화면으로 이동하기 전에, **결과** 현재 탭의 `sessionStorage`에 개인정보가 아닌 완료 시각만 기록한다.

### 사용자 스토리 2 - 약관 및 입력 오류 수정 (우선순위: P2)

사용자는 약관 선택 관계를 이해하고 잘못 입력한 값을 수정하여 가입 가능한 상태를 만든다.

**우선순위 이유**: 제출 전에 오류를 발견하고 수정할 수 있어야 가입 실패와 반복 입력을 줄일 수 있다.

**독립 검증**: 전체 동의와 개별 동의를 변경하고 유효하거나 유효하지 않은 값을 입력하여 오류와 버튼 상태를 확인한다.

**인수 시나리오**:

1. **상황** 모든 약관이 해제되어 있을 때, **동작** 전체 동의를 선택하면, **결과** 서비스 이용약관과 AI 생성 콘텐츠 이용 안내가 모두 선택된다.
2. **상황** 전체 동의가 선택되어 있을 때, **동작** 전체 동의를 해제하면, **결과** 두 개별 약관도 모두 해제된다.
3. **상황** 두 개별 약관이 모두 선택됐을 때, **동작** 선택 상태를 확인하면, **결과** 전체 동의도 선택 상태가 된다.
4. **상황** 개별 약관 중 하나가 해제됐을 때, **동작** 선택 상태를 확인하면, **결과** 전체 동의도 해제 상태가 된다.
5. **상황** 입력값이 비어 있거나 형식·일치 조건을 충족하지 않을 때, **동작** 해당 입력의 검증 시점이 되면, **결과** 원인을 설명하는 오류가 표시되고 가입하기 버튼은 비활성화된다.
6. **상황** 닉네임 또는 이메일의 기본 검증을 통과했을 때, **동작** 중복 확인 시점이 되면, **결과** 사용 가능 여부가 확인되며 중복이면 가입하기 버튼이 활성화되지 않는다.

### 사용자 스토리 3 - 반응형 화면과 기존 계정 이동 (우선순위: P3)

사용자는 데스크톱, 태블릿과 모바일에서 같은 항목과 기능을 확인하고 기존 계정이 있으면 로그인 화면으로 이동한다.

**우선순위 이유**: 기기 크기와 관계없이 동일한 가입 흐름과 명확한 로그인 이동을 제공해야 한다.

**독립 검증**: 1320px, 1024px, 480px 기준 화면에서 구성·순서·넘침 여부를 확인하고 로그인 링크를 선택한다.

**인수 시나리오**:

1. **상황** 각 기준 너비로 회원가입 화면을 열었을 때, **동작** 화면을 확인하면, **결과** 해당 Figma 배치를 따르면서 모든 콘텐츠가 화면 밖으로 넘치거나 잘리지 않는다.
2. **상황** 어떤 기준 화면을 사용하든, **동작** 입력 영역을 확인하면, **결과** `닉네임`, `이메일`, `비밀번호`, `비밀번호 확인` 순서가 동일하다.
3. **상황** 사용자가 `이미 계정이 있습니다.`를 선택했을 때, **동작** 링크 이동이 실행되면, **결과** 로그인 화면(`/login`)으로 이동한다.

### 예외 상황

- 전체 동의는 독립된 필수 약관이 아니라 두 개별 필수 약관의 상태를 한 번에 변경하고 요약하는 제어 항목이다.
- 닉네임이나 이메일의 기본 검증이 실패하면 중복 확인을 요청하지 않고 해당 입력 오류를 우선 표시한다.
- 비밀번호 확인은 비밀번호와 일치하더라도 비밀번호 자체가 `8~16자` 및 조합 조건을 충족하지 않으면 유효하지 않다.
- 회원가입 요청 중에는 입력, 약관과 가입하기 버튼을 조작할 수 없으며 중복 요청이 발생하지 않아야 한다.
- 회원가입 요청의 성공·실패와 관계없이 요청이 끝나면 `isLoading`은 해제되어야 한다.
- UI 우선 단계에는 실제 요청이 없으므로 Loading, 성공 이동, 서버 오류와 로그인 사용자 접근 제한을 실제 동작처럼 흉내 내지 않는다.
- 디자인의 비밀번호 길이 안내는 `8~10자`가 아니라 확정된 `8~16자`로 표시한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 `/signup`에 회원가입 제목, 약관 동의, 회원 정보 입력, 가입하기 버튼과 로그인 이동 링크를 제공해야 한다.
- **FR-002**: 최초 진입 시 모든 입력값과 약관은 비어 있고 입력 오류와 요청 중 상태는 표시되지 않아야 한다.
- **FR-003**: 입력 항목은 모든 화면에서 `닉네임`, `이메일`, `비밀번호`, `비밀번호 확인` 순서로 제공되어야 한다.
- **FR-004**: 약관 영역은 전체 동의, 필수 서비스 이용약관 동의, 필수 AI 생성 콘텐츠 이용 안내 동의로 구성되어야 한다.
- **FR-005**: 전체 동의를 선택하거나 해제하면 두 개별 약관이 같은 상태로 변경되어야 한다.
- **FR-006**: 두 개별 약관이 모두 선택되면 전체 동의도 선택되고, 하나라도 해제되면 전체 동의도 해제되어야 한다.
- **FR-007**: 닉네임은 필수이며 기본 검증을 통과한 값에 대해 중복 여부를 확인해야 한다.
- **FR-008**: 이메일은 필수이며 이메일 형식을 검증한 후 기본 검증을 통과한 값에 대해 중복 여부를 확인해야 한다.
- **FR-009**: 비밀번호는 영문, 숫자와 특수문자를 각각 하나 이상 포함한 `8~16자`여야 한다.
- **FR-010**: 비밀번호와 비밀번호 확인은 마스킹되어야 하며 기존 확정 요구사항에 따라 각각 독립적인 표시·숨김 기능을 제공해야 한다.
- **FR-011**: 비밀번호 확인은 필수이며 유효한 비밀번호와 일치해야 한다.
- **FR-012**: 각 입력 오류는 해당 입력의 검증 시점에 표시하고 유효한 값으로 수정되면 해제해야 한다.
- **FR-013**: 두 필수 약관, 네 입력값의 검증과 닉네임·이메일 중복 확인이 모두 통과한 경우에만 가입하기 버튼을 활성화해야 한다.
- **FR-014**: 실제 회원가입 요청은 닉네임, 이메일과 비밀번호를 사용하며 비밀번호 확인은 일치 검증에만 사용해야 한다.
- **FR-015**: 회원가입 요청 중에는 호출 측 Boolean `isLoading`으로 공통 Loading을 표시하고 모든 입력·약관·제출 조작과 중복 요청을 차단해야 한다.
- **FR-016**: 요청이 성공하거나 실패하면 `isLoading`을 종료하고 화면 상호작용을 복구해야 한다.
- **FR-017**: 회원가입 성공 시 `/signup/complete`로 이동해야 한다.
- **FR-018**: 구분 가능한 회원가입 실패는 사용자가 이해할 수 있는 안내로 제공해야 하며 내부 오류 원문을 노출하지 않아야 한다.
- **FR-019**: `이미 계정이 있습니다.`는 `/login`으로 이동하는 링크여야 한다.
- **FR-020**: 1320px, 1024px와 480px 기준 화면은 각각 연결된 Figma의 배치와 크기 차이를 반영해야 한다.
- **FR-021**: 모든 기준 화면에서 콘텐츠가 화면 밖으로 넘치거나 잘리지 않고 입력 및 버튼을 조작할 수 있어야 한다.
- **FR-022**: 비밀번호 안내 문구는 디자인의 `8~10자` 대신 확정된 `8~16자` 조건을 표시해야 한다.
- **FR-023**: Header는 사이트 공통 영역에서 제공받고 회원가입 페이지가 직접 중복 렌더링해서는 안 된다.
- **FR-024**: `/signup` 최초 진입 시 Header 접힘 요구는 공통 Header 명세와 담당 작업에 의존해야 한다.
- **FR-025**: 입력란과 버튼은 기존 공통 SCSS mixin의 외형을 재사용하되 회원가입 페이지의 배치 차이는 전용 스타일로 표현해야 한다.
- **FR-026**: 회원가입 페이지를 위해 Input 또는 Button 역할의 공통 React 컴포넌트를 새로 생성해서는 안 된다.
- **FR-027**: 회원가입 이벤트 요청에 Suspense fallback 또는 Next.js `loading.js`를 사용해서는 안 된다.
- **FR-028**: UI 우선 단계에서 실제 Supabase 회원가입, API, 세션 저장, 이메일 인증, 가짜 사용자, 가짜 성공 응답, 가짜 중복 결과 또는 테스트용 Promise를 구현해서는 안 된다.
- **FR-029**: UI 우선 단계에서 실제 인증 판정 없이 로그인 사용자 접근용 CommonModal을 미리 연결해서는 안 된다.

### 핵심 엔티티

- **회원가입 정보**: 닉네임, 이메일, 비밀번호와 비밀번호 확인 값이다. 비밀번호 확인은 제출 데이터가 아니라 일치 검증에만 사용한다.
- **약관 동의 상태**: 전체 동의와 두 필수 약관의 선택 여부다. 실제 가입 필수 조건은 두 개별 약관이다.
- **입력 검증 상태**: 필수, 이메일 형식, 비밀번호 조합·길이, 비밀번호 일치와 닉네임·이메일 중복 결과다.
- **회원가입 처리 상태**: 요청 전, 요청 중, 성공과 실패를 나타내며 요청 중 여부는 Boolean `isLoading`으로 표현한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 유효하고 중복되지 않은 정보를 가진 사용자는 5분 이내에 회원가입 입력을 완료할 수 있다.
- **SC-002**: 필수 약관, 입력 검증 또는 중복 확인 중 하나라도 통과하지 않은 상태에서 가입하기 버튼이 활성화되는 사례는 0건이어야 한다.
- **SC-003**: 전체 동의와 개별 약관의 선택·해제 조합이 정의된 관계와 다르게 표시되는 사례는 0건이어야 한다.
- **SC-004**: 닉네임·이메일 중복, 이메일 형식, 비밀번호 조합·길이와 비밀번호 불일치 검증 시나리오가 모두 올바른 결과를 표시해야 한다.
- **SC-005**: 회원가입 요청 중 반복 조작으로 두 건 이상의 요청이 발생하는 사례는 0건이어야 한다.
- **SC-006**: 회원가입 요청의 성공과 실패 검증 모두에서 요청 종료 후 Loading이 제거되고 상호작용이 복구되어야 한다.
- **SC-007**: 1320px, 1024px와 480px 기준 화면 모두에서 입력 순서가 동일하고 필수 화면 요소의 누락·잘림·가로 넘침이 없어야 한다.
- **SC-008**: 모든 화면에서 기존 계정 안내를 한 번 선택해 `/login`에 도달할 수 있어야 한다.
- **SC-009**: 회원가입 페이지에서 공통 Header가 두 개 이상 표시되는 사례는 0건이어야 한다.
- **SC-010**: UI 우선 결과물에서 실제 또는 가짜 회원가입·중복 확인·세션·이메일 인증 동작이 실행되는 사례는 0건이어야 한다.

## 가정 및 후속 연동

- 닉네임과 이메일 중복 여부를 확인할 수 있는 서비스 계약은 인증 연동 단계에서 제공된다.
- 중복 확인 시점은 기존 확정 요구사항대로 각 입력의 기본 검증 통과 후 입력란에서 포커스를 벗어날 때다.
- 실제 회원가입과 중복 확인이 없는 UI 우선 단계에서는 클라이언트에서 판단 가능한 입력·약관 상태만 검증하며, 이를 실제 가입 성공으로 취급하지 않는다.
- 로그인 사용자 접근 제한은 실제 인증 상태를 판정할 수 있는 단계에서 연결하며 공통 모달의 구체적인 동작은 해당 공통 명세를 따른다.
- Header의 구체적인 외형과 동작은 공통 Header 명세를 따르며 회원가입 페이지 작업은 Header와 사이트 공통 영역을 변경하지 않는다.
- 공통 Loading의 외형, 안내, 상호작용 차단과 접근성은 공통 Loading 명세와 계약을 따른다.
- 인증, Supabase 통신, 세션 저장과 이메일 인증 방식은 이 명세에서 결정하지 않는다.
