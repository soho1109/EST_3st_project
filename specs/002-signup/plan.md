# 구현 계획: 회원가입 페이지

**브랜치**: `002-signup` | **작성일**: 2026-08-11 | **명세**: [spec.md](./spec.md)

**입력**: `specs/002-signup/spec.md`의 갱신된 기능 명세

## 요약

`/signup`에 데스크톱 1320px, 태블릿 1024px, 모바일 480px 디자인을 반영한 회원가입 UI를 만든다. 페이지가 약관과 네 입력값, 오류 공개 시점, 비밀번호 표시 상태를 직접 관리한다. 입력·버튼 외형은 기존 SCSS mixin을 재사용하고 Header는 사이트 공통 레이아웃에 맡긴다. 이번 단계에는 클라이언트 검증과 반응형 UI만 포함하며 실제 Supabase 회원가입, 중복 확인, 세션, 이메일 인증, CommonModal 연결과 가짜 요청은 제외한다.

## 기술 배경

**언어/버전**: JavaScript, React 19.2.4

**주요 의존성**: Next.js 16.2.12 App Router, React 19.2.4, Sass 1.102.0

**저장소**: 해당 없음. 이번 단계에서는 브라우저 상태만 사용하고 영속 저장을 하지 않는다.

**테스트**: `npm run dev` 기반 수동 기능·반응형 검증, 마지막 단계의 `npm run lint`

**대상 플랫폼**: 최신 데스크톱·태블릿·모바일 웹 브라우저

**프로젝트 유형**: Next.js 웹 애플리케이션

**성능 목표**: 입력과 약관 변경 결과가 사용자 조작 직후 반영되고, 화면 크기 변경 시 가로 넘침 없이 재배치된다.

**제약 사항**: Header 및 사이트 레이아웃 수정 금지, 새 공통 React Input·Button 금지, 새 패키지 금지, 실제·가짜 인증 및 중복 확인 금지, Suspense와 `loading.js` 금지

**작업 규모**: 회원가입 페이지 1개와 전용 SCSS Module 1개. 기존 `_mixins.scss`, Loading과 공통 Header는 수정하지 않고 재사용 또는 후속 연동 대상으로만 둔다.

## 구현 단계

### 1. 정적 구조와 접근 가능한 폼

- 제목, 구분선, 약관 fieldset, 네 입력란, 가입하기 버튼과 `/login` Link를 의미에 맞는 HTML 요소로 구성한다.
- 입력 순서는 모든 화면에서 닉네임, 이메일, 비밀번호, 비밀번호 확인으로 고정한다.
- label과 input을 명시적으로 연결하고 검증 이후 오류가 생긴 입력에만 `aria-invalid`와 오류 설명 연결을 제공한다.
- 접근성 속성·키보드 제어에는 프로젝트 주석 규칙에 맞춰 목적을 설명하는 주석을 둔다.

### 2. 약관 및 입력 상태

- 닉네임, 이메일, 비밀번호, 비밀번호 확인과 두 개별 약관을 페이지 로컬 Boolean·문자열 상태로 관리한다.
- 전체 동의는 별도 원본 데이터가 아니라 두 개별 약관의 결합 상태에서 계산한다.
- 전체 동의 변경 시 두 개별 상태를 함께 변경하고, 개별 변경 시 계산된 전체 동의가 자동 반영되게 한다.
- 비밀번호와 비밀번호 확인의 표시·숨김 상태는 서로 독립적으로 관리한다.

### 3. 클라이언트 검증과 제출 경계

- 입력별 touched 상태를 사용해 최초 화면에서는 오류를 숨기고 blur 또는 제출 시점 이후 오류를 공개한다.
- 이메일 형식과 비밀번호의 영문·숫자·특수문자 포함 및 8~16자, 비밀번호 일치를 검증한다.
- UI 단계에서 닉네임·이메일 중복 통과 상태를 만들거나 가짜 요청으로 대신하지 않는다.
- `handleSubmit`은 기본 제출을 막고 로컬 오류를 공개하되 Supabase 요청, 성공 이동, Loading 전환을 실행하지 않는다.
- 후속 인증 연동 시 중복 확인 결과까지 통과해야 최종 가입 요청이 가능하도록 계약 경계를 남긴다.

### 4. 공통 스타일과 반응형 배치

- `page.module.scss`에서 `styles/abstracts/colors`, `typography`, `mixins`를 불러온다.
- 입력 외형에는 기존 `mixin.input-base`, 버튼 외형에는 `mixin.button-base`를 재사용한다.
- 1320px 화면은 넓은 중앙 콘텐츠와 라벨·입력의 가로 배치를, 1024px 화면은 축소된 중앙 콘텐츠와 가로 배치를, 480px 화면은 20px 여백 안의 모바일 배치를 따른다.
- `max-width`, 유연한 너비와 `box-sizing`으로 기준점 사이 너비에서도 가로 넘침을 막는다.
- Figma의 태블릿·모바일 `이름`과 8~10자 안내는 각각 `닉네임`, `8~16자`로 교체한다.

### 5. 후속 인증 연동 경계

- 실제 연동 시 페이지가 Boolean `isLoading`을 소유하고 `{isLoading && <Loading />}` 형태로 공통 Loading을 표시한다.
- 실제 요청 시작부터 종료까지 입력, 약관과 제출 버튼을 비활성화하고 `finally`에 해당하는 종료 경로에서 상태를 복구한다.
- 닉네임·이메일 중복 확인, Supabase 회원가입, 이메일 인증, 성공 이동과 인증 사용자 CommonModal은 별도 인증 작업에서 연결한다.
- 이번 구현에서는 이러한 후속 상태나 콜백을 가짜 값으로 선행 작성하지 않는다.

## 검증 전략

- 최초 진입, 약관 전체·개별 선택 관계, 입력별 오류 공개·해제, 비밀번호 표시 전환과 `/login` 이동을 수동 검증한다.
- 1320px, 1024px, 480px 및 481~1023px 중간 너비에서 순서, 정렬, 잘림과 가로 넘침을 확인한다.
- 키보드만으로 입력·체크박스·표시 전환·버튼·로그인 링크에 접근 가능한지 확인한다.
- 실제 네트워크 요청, 가짜 성공, 가짜 중복 결과, CommonModal, Suspense와 `loading.js`가 추가되지 않았는지 확인한다.
- 마지막 작업에서 `npm run lint`를 실행하며 production build는 이 계획의 필수 검증에 포함하지 않는다.
