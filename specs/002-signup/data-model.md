# 데이터 모델: 회원가입 페이지

이번 문서는 UI 상태와 추후 인증 연동 경계를 정의한다. 데이터베이스 스키마나 Supabase 모델은 포함하지 않는다.

## 회원가입 입력 상태

| 필드 | 형식 | 초기값 | 검증 |
|---|---|---|---|
| `nickname` | 문자열 | 빈 문자열 | 공백 제거 후 필수, 추후 중복 확인 |
| `email` | 문자열 | 빈 문자열 | 필수, 이메일 형식, 추후 중복 확인 |
| `password` | 문자열 | 빈 문자열 | 영문·숫자·특수문자 포함, 8~16자 |
| `passwordConfirm` | 문자열 | 빈 문자열 | 필수, 유효한 비밀번호와 일치 |

- `passwordConfirm`은 제출 데이터가 아니라 일치 검증에만 사용한다.
- 실제 인증 요청 데이터는 추후 `nickname`, `email`, `password`로 구성한다.

## 약관 동의 상태

| 필드 | 형식 | 초기값 | 역할 |
|---|---|---|---|
| `isServiceTermsAccepted` | Boolean | `false` | 필수 서비스 이용약관 동의 |
| `isAiTermsAccepted` | Boolean | `false` | 필수 AI 생성 콘텐츠 이용 안내 동의 |
| `isAllTermsAccepted` | 계산된 Boolean | `false` | 두 개별 약관 상태의 논리곱 |

### 상태 전이

- 전체 동의 `false → true`: 두 개별 약관을 모두 `true`로 변경한다.
- 전체 동의 `true → false`: 두 개별 약관을 모두 `false`로 변경한다.
- 개별 약관 하나 해제: 계산된 전체 동의는 즉시 `false`가 된다.
- 두 개별 약관 모두 선택: 계산된 전체 동의는 즉시 `true`가 된다.

## 검증 공개 상태

각 입력에는 사용자가 해당 입력을 벗어났거나 제출을 시도했는지 나타내는 Boolean touched 상태가 대응한다.

| 검증 | 성공 조건 | 오류 공개 조건 |
|---|---|---|
| 닉네임 필수 | 공백 제거 후 값 존재 | 닉네임 touched 이후 |
| 이메일 필수·형식 | 값 존재 및 이메일 형식 통과 | 이메일 touched 이후 |
| 비밀번호 | 값 존재, 조합과 8~16자 통과 | 비밀번호 touched 이후 |
| 비밀번호 확인 | 값 존재 및 비밀번호와 일치 | 비밀번호 확인 touched 이후 |

- 최초 화면에서는 touched가 모두 `false`이므로 오류를 표시하지 않는다.
- 유효한 값으로 수정되면 공개된 오류를 해제한다.
- 닉네임·이메일 중복 상태는 실제 서비스 계약 전에는 생성하지 않는다.

## 비밀번호 표시 상태

- 비밀번호와 비밀번호 확인은 각각 독립된 Boolean 표시 상태를 갖는다.
- 초기값은 모두 `false`이며 입력은 마스킹된다.
- 한 입력의 표시 전환이 다른 입력의 상태를 변경하지 않는다.

## 제출 및 로딩 상태

### UI 우선 단계

- submit 이벤트는 브라우저 기본 제출을 방지하고 로컬 검증 공개만 수행한다.
- 실제 요청 상태, 성공 상태와 실패 상태를 만들지 않는다.

### 후속 인증 연동 단계

- 로컬 검증, 두 필수 약관과 닉네임·이메일 중복 확인이 모두 통과해야 제출 가능하다.
- 요청 시작 시 `isLoading: false → true`, 종료 시 성공·실패와 관계없이 `true → false`로 전환한다.
- 요청 중에는 입력, 약관, 비밀번호 표시 전환과 가입 버튼을 비활성화한다.
