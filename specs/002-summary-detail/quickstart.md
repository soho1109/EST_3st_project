# 빠른 시작 및 검증 안내: 요약 상세 영속 학습노트·북마크

## 목적

팀 Supabase에서 요약본 삭제와 학습노트를 조회·변경하고 로그인 사용자의 학습노트 CRUD와 북마크 저장이 인증·소유권·RLS 규칙에 맞게 동작하는지 검증한다. 필드와 관계는 [데이터 모델](./data-model.md), 인터페이스는 [계약](./contracts/summary-detail-contract.md)을 따른다.

## 사전 조건

- 프로젝트 의존성과 `.env.local`의 팀 Supabase URL·Publishable Key가 준비되어 있다.
- Supabase CLI는 팀 프로젝트에 연결돼 있다.
- DB 변경 내용과 적용 시점을 팀에 공유하고 리뷰 승인을 받았다.
- 테스트에 사용할 실제 Auth 사용자 A와 B가 준비되어 있다.
- Secret Key, `service_role` Key, Access Token과 DB 비밀번호를 코드·문서·명령 출력에 남기지 않는다.

## 마이그레이션 검증과 적용

연결 대상 project ref와 원격 마이그레이션 상태를 먼저 확인하고 DB lint를 실행한다.

```bash
npx supabase projects list
npx supabase migration list
npx supabase db lint --linked
```

적용 전 dry-run 결과와 SQL, 대상 project ref, 백업·PITR 또는 복구 지점, 실패 복구 절차를 팀에서 검토한다.

```bash
npx supabase db push --dry-run
```

승인된 마이그레이션만 팀 DB에 적용한다.

```bash
npx supabase db push
```

**예상 결과**:

- 기존 `profiles` 컬럼·데이터·정책은 변경되지 않는다.
- `summaries`, `learning_notes`, `bookmarks`와 제한된 작성자 닉네임 함수가 생성된다.
- 신규 테이블에 RLS, 최소 GRANT, CHECK·FK·유일 제약과 필요한 인덱스가 적용된다.
- 마이그레이션에는 테스트 데이터가 포함되지 않는다.

## 임시 테스트 데이터 준비

팀 DB 관리 화면에서 사용자 A의 Auth UUID를 작성자로 참조하는 공개 요약본 한 건만 임시 등록한다. `ai_summary`는 [데이터 모델](./data-model.md)의 화면 구조를 따른다.

기존 `src/mocks` JSON은 삽입하지 않는다. 요약본 생성 UI나 서비스 역할 키를 애플리케이션에 추가하지 않는다.

## 애플리케이션 실행

```bash
npm run dev
```

임시 요약본 UUID를 사용해 `/summary/{summaryId}`를 연다.

먼저 `/summary` 목록에서 임시 요약본 링크가 같은 UUID 상세로 연결되는지 확인한다.

## 시나리오 1: 공개 요약본과 학습노트 조회

1. 비로그인 상태에서 임시 공개 요약본을 연다.
2. 주제와 AI 요약이 DB 값과 일치하는지 확인한다.
3. 사용자 A와 B가 학습노트를 생성한 뒤 목록을 다시 연다.
4. 목록이 현재 요약본 항목만 `created_at`, `id` 내림차순으로 표시하는지 확인한다.
5. 작성자 닉네임 또는 fallback, 작성일과 퀴즈 상태를 확인한다.
6. 존재하지 않는 UUID와 다른 상위 요약본의 학습노트 경로를 연다.

**예상 결과**: 공개 데이터는 정확히 표시되고 존재하지 않거나 관계가 다른 경로는 404 처리된다.

## 시나리오 2: 비공개 요약본 경계

1. 관리 화면에서 임시 요약본을 비공개로 변경한다.
2. 비로그인 또는 사용자 B로 경로를 연다.
3. 사용자 A로 같은 경로를 연다.
4. 검증 후 다시 공개 상태로 돌린다.

**예상 결과**: 비작성자에게 보호 콘텐츠가 노출되지 않고 작성자만 조회할 수 있다. 비밀번호 잠금은 이번 증분 완료로 취급하지 않는다.

## 시나리오 3: 학습노트 생성과 입력 검증

1. 비로그인 상태로 `/summary/{summaryId}/notes/new`에 접근한다.
2. 사용자 A로 로그인해 빈 제목과 50자를 초과한 제목을 제출한다.
3. 유효한 제목과 선택 본문을 제출한다.
4. 생성된 상세를 새로고침하고 요약 목록으로 돌아간다.

**예상 결과**:

- 비로그인 직접 접근은 `/login`으로 이동한다.
- 유효하지 않은 입력은 행을 생성하지 않는다.
- 유효한 입력은 인증 사용자를 작성자로 한 행 하나를 만들고 생성된 상세로 이동한다.
- 새로고침 후 내용이 유지되고 목록 최상단에 표시된다.

## 시나리오 4: 학습노트 수정과 소유권

1. 사용자 A가 자신이 만든 학습노트 수정 경로를 열고 값을 수정한다.
2. 상세·목록·수정 화면에서 변경값을 확인한다.
3. 사용자 B로 같은 수정 URL과 Action 직접 호출을 시도한다.

**예상 결과**: 사용자 A의 변경만 저장된다. 사용자 B의 페이지 접근은 현재 요약 상세로 이동하고 직접 변경은 RLS에서 차단된다.

## 시나리오 5: 학습노트 삭제

1. 사용자 B로 사용자 A의 학습노트 삭제를 시도한다.
2. 사용자 A로 삭제 확인 모달에서 취소한다.
3. 다시 삭제를 승인한다.
4. 삭제된 직접 경로와 현재 요약 목록을 확인한다.

**예상 결과**:

- 비작성자 요청과 취소는 데이터를 변경하지 않는다.
- 작성자 확인 후 한 행만 삭제되고 `/summary/{summaryId}`로 이동한다.
- 삭제한 항목은 목록에 없고 직접 경로는 404다.

## 시나리오 6: 요약본 삭제

1. 사용자 A가 작성한 학습노트가 없는 요약본을 연다.
2. 요약본 작성자에게만 `삭제` 버튼이 표시되는지 확인한다.
3. 삭제 확인 모달에서 `취소`를 선택하고 현재 페이지와 데이터가 유지되는지 확인한다.
4. 다시 삭제를 선택하고 확인 모달에서 `삭제`를 승인한다.
5. `/allnote`로 이동하는지 확인하고 요약본이 제거됐는지 확인한다.
6. 학습노트가 있는 요약본을 사용자 A로 열어 삭제 버튼이 표시되지 않는지 확인한다.
7. 사용자 B 또는 비로그인 상태에서는 삭제 버튼이 표시되지 않고 직접 요청도 차단되는지 확인한다.

**예상 결과**: 학습노트가 없는 요약본만 작성자 승인 후 삭제되고 `/allnote`로 이동한다. 학습노트가 있는 요약본, 취소, 비작성자 요청은 데이터를 변경하지 않는다.

## 시나리오 7: 북마크 저장·해제와 중복 방지

1. 비로그인 상태에서 북마크 버튼을 선택한다.
2. 사용자 A로 로그인해 북마크를 저장한다.
3. 저장 요청을 반복하거나 빠르게 선택한다.
4. 페이지를 새로고침해 상태를 확인한다.
5. 북마크를 해제하고 다시 새로고침한다.

**예상 결과**:

- 비로그인은 저장하지 않고 로그인 안내를 받는다.
- 동일 사용자·요약본 관계는 한 건만 존재한다.
- 새로고침 후 마지막 확정 상태가 유지된다.
- 해제 후 관계가 제거된다.
- `/mypage/bookmarks`의 영속 목록 전환은 별도 목록 기능에서 검증한다.

## 시나리오 8: 실패와 중복 제출

1. 실패하도록 만든 환경에서 학습노트 생성·수정과 북마크 변경을 시도한다.
2. 처리 중 버튼을 연속 선택한다.
3. 복구 후 페이지를 다시 조회한다.

**예상 결과**: 중복 요청이 차단되고 입력값과 마지막 확정 상태가 보존되며 실패를 성공으로 안내하지 않는다.

## RLS 검증 행렬

일반 인증 세션으로 검증하며 서비스 역할 키를 사용하지 않는다.

| 요청 | 사용자 A | 사용자 B | 비로그인 |
|---|---|---|---|
| 공개 요약본 SELECT | 허용 | 허용 | 허용 |
| A의 비공개 요약본 SELECT | 허용 | 차단 | 차단 |
| A 작성 요약본 DELETE | 허용 | 차단 | 차단 |
| 공개 요약본 학습노트 SELECT | 허용 | 허용 | 허용 |
| A 작성 학습노트 UPDATE·DELETE | 허용 | 차단 | 차단 |
| A 명의 학습노트 INSERT | 허용 | 차단 | 차단 |
| A 북마크 SELECT·INSERT·DELETE | 허용 | 차단 | 차단 |

## 임시 데이터 정리

검증이 끝나면 테스트 중 생성된 학습노트를 먼저 제거한 뒤 학습노트가 없는 임시 요약본을 제거한다. 팀원의 실제 데이터와 기존 Profile은 삭제하지 않는다.

## 정적 검증

```bash
npx supabase db lint --linked
npm run lint
npm run build
git diff --check
```

**통과 기준**:

- 새 DB lint·코드 오류가 없다.
- 기존 mock JSON, `profiles`, 공통 Supabase 클라이언트와 Proxy가 변경되지 않는다.
- 비작성자와 비로그인 쓰기로 변경된 행이 0건이다.
- 중복 북마크가 0건이다.
- 요약본 생성·수정, 잠금 인증과 퀴즈 저장이 추가되지 않는다. 요약본 삭제는 시나리오 6 범위로 검증한다.
