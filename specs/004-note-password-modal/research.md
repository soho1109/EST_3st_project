# 조사 결과: 요약 노트 비밀번호 모달

## 결정 1: Client Component 경계

**결정**: `NotePwModal.jsx`에만 `"use client"`를 선언한다.

**근거**: 비밀번호 입력 상태, 클릭과 폼 제출 이벤트, 검증 중 비활성 상태 반영이 필요하다. Next.js 공식 문서는 상태와 이벤트 핸들러가 필요한 상호작용 UI를 Client Component로 구성하도록 안내한다. 호출 페이지 전체를 Client Component로 바꿀 필요는 없으며 필요한 상호작용 경계만 작게 유지한다.

**검토한 대안**:

- 호출 페이지 전체를 Client Component로 전환: 불필요한 클라이언트 경계를 넓히므로 제외한다.
- Server Component만 사용: 입력 상태와 이벤트 처리가 필요하므로 불가능하다.

**참고**: [Next.js Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)

## 결정 2: 버튼과 Enter 제출 통합

**결정**: 비밀번호 입력과 `type="submit"` 버튼을 하나의 `<form onSubmit>`에 넣고 제출 로직을 `handleSubmit`으로 통합한다.

**근거**: 브라우저의 표준 폼 동작으로 버튼과 Enter 키가 같은 제출 경로를 사용한다. React 공식 문서에 따라 `onSubmit`에서 기본 페이지 새로고침을 막은 뒤 현재 입력값을 콜백으로 전달한다.

**검토한 대안**:

- 입력의 `onKeyDown`에서 Enter를 별도 처리: 버튼 로직과 중복되고 두 경로의 동작이 달라질 수 있어 제외한다.
- form action 또는 Server Action: 백엔드 통신 구조가 정해지지 않았고 이번 범위를 넘어가므로 제외한다.

**참고**: [React form reference](https://react.dev/reference/react-dom/components/form)

## 결정 3: 상태 소유권과 props 계약

**결정**: 비밀번호 문자열은 모달 내부에서 관리하고, 공개 여부·검증 진행·검증 오류와 후속 동작은 호출 측이 관리한다.

**근거**: 입력 문자열은 모달의 일시적인 UI 상태인 반면 검증, 이동, 세션 인증, 공통 오류 표시는 페이지 문맥과 백엔드에 의존한다. 이를 분리하면 백엔드 미연결 상태에서도 UI를 독립 검증할 수 있고 향후 실제 검증 수단으로 교체할 수 있다.

**검토한 대안**:

- 모든 상태를 모달 내부에서 관리: 라우팅과 시스템 오류 모달까지 결합되어 재사용성이 떨어지고 통신 구조를 추정하게 된다.
- 입력값까지 부모가 관리: 호출 측에 불필요한 타이핑 상태를 노출하므로 제외한다.

비밀번호 입력은 유효한 제출을 호출 측에 전달한 직후 초기화한다. 오류 문자열의 변경을 감시하는 Effect에 의존하지 않으므로 같은 불일치 결과가 반복되어도 매번 빈 입력에서 재시도할 수 있다.

## 결정 4: 잘못된 비밀번호와 시스템 오류 구분

**결정**: 잘못된 비밀번호는 `errorMessage`로 모달 안에 표시하고, 시스템 오류는 호출 측이 모달을 닫은 뒤 공통 오류 모달로 처리한다.

**근거**: 명세가 두 실패 유형을 명확히 구분한다. 현재 `CommonModal.jsx`가 없으므로 `NotePwModal`에서 이를 import하거나 대체 구현하지 않는다.

**검토한 대안**:

- 모든 오류를 모달 내부에 표시: 시스템 오류 처리 명세와 충돌한다.
- `NotePwModal`이 `CommonModal`까지 렌더링: 공통 컴포넌트 책임을 중복하고 현재 코드에 없는 계약을 추정하게 되어 제외한다.

## 결정 5: 동일 브라우저 세션 인증

**결정**: 세션 인증의 저장 방식은 모달 밖의 인증·데이터 계층 책임으로 남기고 이번 계획에서는 구현하지 않는다.

**근거**: 명세에는 유지 범위만 있고 저장 위치, 보안 방식, 서버 계약이 정의되지 않았다. `sessionStorage` 같은 클라이언트 저장 방식을 임의 선택하면 보호 경로의 보안 구조를 잘못 확정할 수 있다.

**검토한 대안**:

- `sessionStorage`에 직접 저장: 클라이언트가 조작할 수 있고 서버 보호 여부가 정의되지 않아 제외한다.
- 쿠키 또는 Supabase 세션 사용: 백엔드·인증 계약이 정해지지 않아 현 단계에서 결정하지 않는다.

## 결정 6: 모달 배경과 닫기 방식

**결정**: 고정 배경막으로 화면을 덮고 배경막 클릭은 닫기나 뒤쪽 페이지 동작을 발생시키지 않는다. 닫기는 우측 상단의 명시적 닫기 버튼으로만 제공한다.

**근거**: 제공된 디자인과 FR-002, FR-004, FR-013, FR-014를 그대로 반영한다.

**검토한 대안**:

- 배경막 클릭으로 닫기: FR-014와 충돌하므로 제외한다.
- 네이티브 `<dialog>`의 기본 취소 동작 사용: 명세에 없는 Escape 닫기 동작이 추가될 수 있어 현 범위에서는 제외한다.
