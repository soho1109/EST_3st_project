# 기능 명세: 공통 전체 화면 로딩

**기능 브랜치**: `feature/loading`

**작성일**: 2026-08-09

**상태**: 계획 준비 완료

**입력**: 사용자 설명: 공통 전체 화면 로딩 컴포넌트를 제공하고, 사용자 요청은 호출 측 로딩 상태로, 비동기 콘텐츠 렌더링은 필요한 Suspense 경계로 제어하며 중복 로딩을 방지한다.

## 디자인 참조

- 사용자 첨부 이미지의 전체 화면 로딩 디자인
- 연한 회색 배경막이 화면 전체를 덮는다.
- 화면 중앙에는 `public/images/clear.webp`와 그 주변의 흰색 막대형 진행 표시를 배치한다.
- 진행 표시의 막대 12개는 원형으로 배치하고 투명도가 순서대로 바뀌는 애니메이션을 반복한다.
- 진행 표시 아래에는 `잠시만 기다려주세요.`와 `로딩중입니다`를 두 줄로 표시한다.
- 크기, 색상, 투명도와 간격은 첨부 디자인을 기준으로 한다.

## 관련 명세

- 로그인 페이지는 로그인 요청 중 전체 화면 진행 상태와 모든 인증 동작 차단을 요구한다.
- 회원가입은 요청 중 전체 화면 로딩과 중복 요청 차단을 요구한다.
- 메인 페이지와 요약 노트 상세는 생성·수정 요청 중 진행 상태와 중복 요청 차단을 요구한다.
- 전체 요약 노트, 내 요약 노트와 내 북마크 목록은 같은 목록 구조를 사용하며 최초 조회와 추가 조회에 동일한 공통 로딩 표현을 요구한다.
- 위 목록 요구는 `/summary`, `/mypage/summaries`, `/mypage/bookmarks`에 동일하게 적용한다.
- 기존 명세에서 확인된 공통 로딩 요구와 이번 명세 사이에 충돌은 없다.

## 범위와 책임

- 공통 로딩은 전체 화면 로딩 표현과 뒤쪽 화면의 상호작용 차단만 담당한다.
- 로딩 표시 여부와 종료 시점은 비동기 작업을 소유한 호출 측이 결정한다.
- 사용자 동작으로 시작되는 요청은 호출 측의 Boolean `isLoading` 상태로 표시 여부를 제어하는 방식을 권장한다.
- 비동기 콘텐츠 렌더링을 기다릴 때는 필요한 Suspense 경계의 대체 화면으로 사용할 수 있다.
- 실제 요청, 인증, 데이터 처리, Promise 상태 판정, 페이지 이동, 새로고침과 오류 처리는 범위에 포함하지 않는다.
- 별도 명세에서 다른 로딩 표현을 명시하지 않은 한 프로젝트에서 로딩이 필요한 화면과 영역은 이 공통 전체 화면 로딩을 기본으로 사용한다.

## 사용자 시나리오 및 테스트 _(필수)_

### 사용자 스토리 1 - 요청 중 전체 화면 로딩 확인 (우선순위: P1)

사용자는 로그인, 저장, 삭제 또는 제출 요청이 처리되는 동안 화면이 처리 중임을 확인하고 중복 조작을 하지 않는다.

**우선순위 이유**: 처리 상태를 즉시 전달하고 뒤쪽 화면의 중복 입력을 차단하는 것이 공통 로딩의 핵심 가치다.

**독립 검증**: 개발 확인 화면에서 로딩을 열고 닫아 전체 화면 표시, 애니메이션, 뒤쪽 상호작용 차단과 제거를 검증한다.

**인수 시나리오**:

1. **상황** 호출 화면이 비동기 요청을 시작했을 때, **동작** 로딩 표시 상태를 활성화하면, **결과** 전체 화면에 공통 로딩이 한 번 표시된다.
2. **상황** 공통 로딩이 표시됐을 때, **동작** 사용자가 뒤쪽 화면을 클릭하거나 조작하려 하면, **결과** 뒤쪽 화면에 상호작용이 전달되지 않는다.
3. **상황** 비동기 요청이 종료됐을 때, **동작** 호출 화면이 로딩 표시 상태를 해제하면, **결과** 공통 로딩이 제거되고 뒤쪽 화면을 다시 조작할 수 있다.

---

### 사용자 스토리 2 - 일관된 로딩 디자인 확인 (우선순위: P2)

사용자는 여러 화면의 전체 로딩에서 동일한 이미지, 막대형 진행 표시와 안내 문구를 확인한다.

**우선순위 이유**: 동일한 처리 상태를 일관된 시각 언어로 제공해야 사용자가 상황을 빠르게 이해할 수 있다.

**독립 검증**: 공통 로딩을 단독 표시해 첨부 디자인과 주요 시각 요소를 비교한다.

**인수 시나리오**:

1. **상황** 공통 로딩이 표시됐을 때, **동작** 중앙 표시를 확인하면, **결과** 프로필 이미지와 그 주변의 막대형 진행 표시가 화면 중앙에 나타난다.
2. **상황** 공통 로딩이 표시됐을 때, **동작** 안내 영역을 확인하면, **결과** `잠시만 기다려주세요.`와 `로딩중입니다`가 디자인과 같은 두 줄 구성으로 나타난다.
3. **상황** 공통 로딩이 유지될 때, **동작** 진행 표시를 관찰하면, **결과** 12개 막대의 투명도가 순서대로 바뀌며 처리 중임을 나타낸다.

---

### 사용자 스토리 3 - 로딩 제어 방식 구분 (우선순위: P3)

개발자는 비동기 작업의 종류에 맞는 한 가지 표시 방식으로 공통 로딩을 사용하여 중복 표시를 방지한다.

**우선순위 이유**: 자동 경계와 수동 상태를 동시에 사용하면 예상하지 못한 중복 로딩이 발생할 수 있다.

**독립 검증**: 사용자 요청 상태와 비동기 콘텐츠 대기 사례에서 각각 하나의 제어 방식만 사용해 전체 화면 로딩이 한 번만 표시되는지 확인한다.

**인수 시나리오**:

1. **상황** 사용자 이벤트로 비동기 요청이 시작됐을 때, **동작** 호출 측이 `isLoading` 상태를 활성화하면, **결과** 공통 로딩이 표시되고 해당 이벤트의 Promise를 Suspense가 자동 처리한다고 가정하지 않는다.
2. **상황** 비동기 콘텐츠 렌더링이 지연될 때, **동작** 해당 콘텐츠의 Suspense 대체 화면으로 공통 로딩을 사용하면, **결과** 콘텐츠가 준비될 때까지 공통 로딩이 표시된다.
3. **상황** 하나의 비동기 작업이 진행될 때, **동작** 로딩 표시 구성을 확인하면, **결과** 수동 로딩 상태와 Suspense 대체 화면이 같은 전체 화면 로딩을 동시에 표시하지 않는다.

### 예외 상황

- 로딩이 표시되는 동안 배경막 클릭, 키보드 입력과 포인터 입력으로 뒤쪽 화면을 조작할 수 없다.
- 로딩에는 닫기, 확인, 취소 버튼이 없으며 사용자가 임의로 종료할 수 없다.
- 호출 측이 로딩을 제거해도 공통 로딩은 성공, 실패 또는 이동을 자체적으로 실행하지 않는다.
- 여러 비동기 작업이 겹치더라도 전체 화면 로딩이 둘 이상 겹쳐 표시되어서는 안 된다.
- 일부 영역의 데이터만 기다리는 상황이라도 별도의 로딩 표현이 명세되지 않았다면 공통 전체 화면 로딩을 사용한다.
- 경로 단위의 자동 로딩 파일은 사용하지 않는다.

## 요구사항 _(필수)_

### 기능 요구사항

- **FR-001**: 시스템은 여러 화면에서 재사용할 수 있는 공통 전체 화면 로딩을 제공해야 한다.
- **FR-002**: 공통 로딩은 화면 전체를 연한 회색 계열 배경막으로 덮어야 한다.
- **FR-003**: 공통 로딩이 표시되는 동안 뒤쪽 화면의 포인터와 키보드 상호작용을 차단해야 한다.
- **FR-004**: 공통 로딩은 화면 중앙에 `clear.webp` 이미지와 주변의 흰색 막대형 진행 표시를 제공해야 한다.
- **FR-005**: 막대형 진행 표시는 로딩이 표시되는 동안 12개 막대의 투명도를 순서대로 변경하는 애니메이션을 반복해야 한다.
- **FR-006**: 공통 로딩은 진행 표시 아래에 `잠시만 기다려주세요.`와 `로딩중입니다`를 두 줄로 표시해야 한다.
- **FR-007**: 배치, 크기, 색상, 투명도와 간격은 첨부 디자인을 따라야 한다.
- **FR-008**: 공통 로딩은 닫기, 확인 또는 취소 동작을 제공해서는 안 된다.
- **FR-009**: 공통 로딩은 표시 여부 또는 비동기 작업 상태를 직접 생성하거나 변경해서는 안 된다.
- **FR-010**: 공통 로딩은 API 호출, 인증, 데이터 요청, Promise 판정, 오류 처리, 페이지 이동과 새로고침을 직접 수행해서는 안 된다.
- **FR-011**: 사용자 이벤트 요청은 호출 측에서 관리하는 Boolean `isLoading` 상태로 공통 로딩의 표시와 제거를 제어하는 방식을 우선 사용해야 한다.
- **FR-012**: 비동기 콘텐츠 렌더링은 필요한 Suspense 경계에서 공통 로딩을 대체 화면으로 사용할 수 있어야 한다.
- **FR-013**: 사용자 이벤트 요청의 Promise가 Suspense만으로 자동 처리된다고 가정해서는 안 된다.
- **FR-014**: 하나의 비동기 작업은 하나의 전체 화면 로딩 표시 책임만 가져야 한다.
- **FR-015**: 동일한 작업에서 호출 측 로딩 상태와 Suspense 대체 화면으로 전체 화면 로딩을 동시에 표시해서는 안 된다.
- **FR-016**: 여러 Suspense 경계가 전체 화면 로딩을 동시에 표시해서는 안 된다.
- **FR-017**: 경로 단위의 자동 로딩 파일을 생성하거나 사용해서는 안 된다.
- **FR-018**: 별도 명세가 다른 로딩 표현을 요구하지 않는 한, 전체 화면과 부분 영역을 포함하여 로딩이 필요한 화면은 공통 전체 화면 로딩을 기본으로 사용해야 한다.
- **FR-019**: 공통 로딩의 파일과 스타일은 각각 `src/components/Loading.jsx`, `src/components/Loading.module.scss`에 대응해야 한다.
- **FR-020**: 개발 확인 화면은 `src/app/(dev)/dev/loading/page.js`에 대응하고 기존 개발 메인 화면을 변경하지 않아야 한다.
- **FR-021**: 이 기능을 위해 새로운 패키지 또는 상태 관리 도구를 추가해서는 안 된다.

### 핵심 엔티티

- **로딩 공개 상태**: 호출 측이 전체 화면 로딩을 표시하거나 제거할지 결정하는 Boolean `isLoading` 상태다.
- **로딩 표시 내용**: 배경막, 프로필 이미지, 순차적으로 투명도가 바뀌는 막대형 진행 표시와 두 줄 안내 문구로 구성된다.
- **로딩 소유자**: 현재 비동기 작업의 시작과 종료를 알고 로딩 공개 상태 또는 Suspense 경계를 관리하는 호출 영역이다.

## 성공 기준 _(필수)_

### 측정 가능한 결과

- **SC-001**: 공통 로딩이 표시된 모든 검증 사례에서 화면 전체가 덮이고 뒤쪽 화면에 전달되는 사용자 상호작용은 0건이어야 한다.
- **SC-002**: 디자인 비교 시 프로필 이미지, 막대형 진행 표시와 두 줄 안내 문구의 주요 요소가 100% 표시되어야 한다.
- **SC-003**: 로딩이 유지되는 동안 12개 막대의 순차적 투명도 애니메이션이 멈추는 사례는 0건이어야 한다.
- **SC-004**: 호출 측이 로딩을 제거한 모든 검증 사례에서 공통 로딩이 사라지고 뒤쪽 화면의 상호작용이 복구되어야 한다.
- **SC-005**: 하나의 비동기 작업에서 전체 화면 로딩이 두 개 이상 겹쳐 표시되는 사례는 0건이어야 한다.
- **SC-006**: 공통 로딩이 직접 요청, 상태 판정, 오류 처리 또는 이동을 실행하는 사례는 0건이어야 한다.

## 가정

- `public/images/clear.webp` 자산은 현재 이름과 위치를 유지한다.
- 로딩을 호출하는 영역은 비동기 작업의 시작과 종료를 판단할 수 있다.
- 사용자 이벤트 요청은 호출 측의 `isLoading` 상태로, 비동기 콘텐츠 렌더링은 필요한 Suspense 경계로 구분할 수 있다.
- 첨부 디자인은 데스크톱 전체 화면 기준이며 별도의 모바일 디자인은 제공되지 않았다.
