# 구현 계획: 로그인 페이지

**브랜치**: `feature/login-page` | **작성일**: 2026-08-09 | **명세**: [spec.md](./spec.md)

**입력**: `/specs/003-login-page/spec.md`의 수정된 기능 명세

## 요약

`/login`에 이메일·비밀번호 로그인 폼, 기본 세션 유지 안내, 카카오·구글 로그인 버튼과 회원가입 이동 UI를 구성한다. 데스크톱 `1320px`, 태블릿 `1024px`, 모바일 `480px` 디자인의 구조와 크기 변화를 반영한다. 로그인 페이지는 사이트 레이아웃의 공통 Header를 그대로 사용하고 요청 중 표시에는 공통 `Loading`을 재사용한다. 로그인 사용자 접근 및 시스템 장애용 `CommonModal`은 실제 인증 결과가 제공되는 후속 연동 단계에서 연결한다. 세션 저장 방식을 선택하는 상태는 두지 않고 로그인 성공 후 Supabase 기본 세션 정책을 사용한다.

## 기술 배경

**언어/버전**: JavaScript, React 19.2.4

**주요 의존성**: Next.js 16.2.12 App Router, Sass 1.102.x, `next/image`, `next/link`

**저장소**: 이번 범위에서는 사용하지 않음

**테스트**: `npm run dev` 기반 수동 검증, ESLint

**대상 플랫폼**: 데스크톱·태블릿·모바일 웹 브라우저

**프로젝트 유형**: Next.js 웹 애플리케이션

**성능 목표**: 사용자 입력에 즉시 검증 결과를 표시하고, 요청 상태가 연결된 이후에는 한 요청당 전체 화면 Loading을 하나만 표시한다.

**제약 사항**: Header 및 사이트 레이아웃 수정 금지, `loading.js`와 Suspense fallback 미사용, 실제 인증·OAuth·API·세션 저장·복구 미구현, `localStorage`·`sessionStorage`·Cookie 방식 결정 금지, Pro 세션 제한 기능 제외, 가짜 로그인 성공 및 가짜 세션 저장 금지, 새 패키지와 상태 관리 도구 추가 금지

**작업 규모**: 로그인 페이지 1개, 대응 SCSS Module 1개, 기존 공통 SCSS mixin 파일 1개 확장, 기존 공통 컴포넌트 2개와 이미지 자산 2개 재사용

## 구현 설계

### 페이지 경계와 상태

- 입력값, 입력란 이탈 여부, 폼 오류와 `isLoading`을 다루므로 로그인 페이지를 Client Component로 구성한다.
- 이메일과 비밀번호는 페이지가 제어하며 이메일 형식과 필수값 검증 결과는 이메일·비밀번호·로그인 버튼 영역 하단의 고정된 단일 오류 공간에 우선순위에 따라 한 문구만 표시한다.
- 로그인 버튼은 이메일과 비밀번호 기본 검증을 모두 통과하고 `isLoading`이 아닐 때만 활성화한다.
- 실제 인증 계약이 없는 UI 단계에서는 로그인 성공, 사용자 상태 갱신, 세션 저장 또는 메인 이동을 가짜로 실행하지 않는다.

### 공통 Loading 사용

- 추후 로그인 요청을 연결할 이벤트 처리 영역이 Boolean `isLoading`을 소유한다.
- 요청 시작 시 `true`, 성공·실패와 관계없이 종료 시 `false`로 복구하며 요청 중 모든 로그인 입력과 인증 버튼을 비활성화한다.
- 로그인 이벤트 요청에는 Suspense fallback을 사용하지 않고 `loading.js`도 생성하지 않는다.
- 동일한 요청에서 공통 Loading을 두 번 렌더링하지 않는다.

### 오류와 공통 모달

- 필수 입력, 이메일 형식, 이메일 또는 비밀번호 불일치는 폼 내부 오류로 표시한다.
- 자격 정보 불일치가 401이어도 `CommonModal`의 `error` 모드를 열지 않는다. 이메일은 유지하고 비밀번호는 초기화한다.
- 실제 인증 연동 단계에서 서버·서비스 또는 네트워크 장애에만 `CommonModal`의 `error` 모드와 정규화된 `status`를 사용한다.
- 실제 인증 연동 단계에서 로그인 사용자의 `/login` 접근은 `alreadyLoggedIn` 모드를 사용하며 이동 시간과 닫기 동작은 기존 CommonModal이 담당한다.
- 로그인 사용자 판정과 오류 상태 제공이 없는 UI 단계에서는 CommonModal용 임시 상태나 항상 닫힌 렌더링 경계를 만들지 않는다.

### 이동과 이미지

- 회원가입은 목적지가 고정된 내부 경로이므로 `/signup`을 가리키는 `Link`를 사용한다.
- 카카오 버튼은 `/images/kakao-icon.svg`, 구글 버튼은 `/images/google-icon.svg`를 사용하고 제공자 이름을 텍스트로도 구분한다.
- 소셜 로그인 버튼은 UI를 구성하되 이번 단계에서 OAuth 화면 이동이나 성공 처리를 연결하지 않는다.

### 그리드와 공통 SCSS

- 데스크톱은 `1320px`, 12개 `88px` 컬럼, `24px` gutter와 `24px` row를 기준으로 한다. 로그인 전체 영역은 `644px`, 입력 묶음은 `534px`, 입력과 버튼 간격은 `24px`, 로그인 버튼은 `87px`, 소셜 버튼은 `56px`다.
- 태블릿은 `1024px`, 8개 컬럼, 좌우 margin `32px`, gutter `24px`를 기준으로 한다. 로그인 전체 영역은 `534px`, 입력 묶음은 `423px`, 입력과 버튼 간격은 `24px`, 로그인 버튼은 `87px`, 소셜 버튼은 `48px`다.
- 모바일은 `480px`, 4개 컬럼, 좌우 margin `20px`, gutter `16px`를 기준으로 한다. 로그인 전체 영역은 `440px`, 입력 묶음은 `325px`, 입력과 버튼 간격은 `17px`, 로그인 버튼은 `98px`, 소셜 버튼은 `48px`다.
- 로고는 데스크톱·태블릿에서 `419px × 180px`, 모바일에서 `212px × 91px`를 사용한다.
- 모든 화면의 배경은 `#FBFAF9`, Input 그림자는 `0 0 10px rgba(110, 110, 110, 0.3)`, placeholder는 `16px` Medium `#ACACAC`로 통일한다.
- 모든 화면에서 첫 번째 입력은 `이메일`을 사용하고, 로그인 폼 아래에 Material Symbols `info` 아이콘과 기본 세션 유지 안내를 표시한다.
- `_mixins.scss`에 Input 공통 외형 mixin을 추가해 `1px solid #ACACAC`, `5px` radius, `0 0 10px rgba(110, 110, 110, 0.3)` 그림자와 공통 내부 정렬을 제공한다.
- `page.module.scss`에서는 `@use "styles/abstracts/mixins" as mixin;` 형식으로 공통 mixin을 불러오며 `@/styles/...` 또는 긴 상대 경로를 혼용하지 않는다.
- `_mixins.scss`에 버튼 공통 외형 mixin을 추가하고 배경색과 너비를 인자로 받을 수 있게 한다. 페이지별 배치나 고유 크기는 `page.module.scss`가 담당한다.
- 로그인 Input과 버튼은 공통 mixin을 사용하지만 별도 공통 React 컴포넌트는 만들지 않는다.
- 이메일과 비밀번호 아이콘은 기존 Material Symbols 설정을 재사용해 각각 `person`, `lock`을 표시한다.

### 스타일과 접근성

- 로그인 페이지 전용 스타일은 `page.module.scss`에 작성하고 기존 색상·타이포그래피 토큰을 우선 사용한다.
- 입력은 연결된 label 또는 동등한 이름을 제공하고, 오류 문구는 해당 입력과 연관되어 보조기술이 오류를 식별할 수 있게 한다.
- 아이콘만으로 로그인 제공자를 전달하지 않고 버튼의 텍스트 이름을 유지한다.
- 접근성 속성과 요청 중 비활성화의 목적처럼 코드만으로 의도가 불명확한 부분에는 AGENTS.md 주석 규칙에 맞는 설명을 둔다.

## 구현 단계 구분

### 1단계: UI 우선 구현

1. `_mixins.scss`에 Input과 버튼의 공통 외형 mixin을 추가한다.
2. 로그인 페이지의 그리드 기준 레이아웃과 전용 스타일을 작성하고 공통 mixin을 적용한다.
3. 이메일·비밀번호 상태와 클라이언트 입력 검증을 구성한다.
4. Material Symbols 입력 아이콘, 카카오·구글 이미지와 회원가입 `Link`를 포함한 UI를 구성한다.
5. 공통 Loading을 계약에 맞게 배치하되 CommonModal은 실제 인증 결과가 제공되는 후속 단계로 남긴다.
6. 초기 상태, 입력 검증, 버튼 활성화, 지정 자산과 공통 컴포넌트 중복 여부를 검증한다.

### 2단계: 인증 계약 확정 후 연동

1. 이메일 로그인 및 소셜 OAuth 호출을 확정된 인증 계약에 연결한다.
2. 요청 생명주기에 `isLoading`을 연결하고 종료 시 항상 해제한다.
3. 자격 정보 실패와 시스템 장애를 구분해 폼 오류 또는 CommonModal로 전달한다.
4. 성공한 실제 인증 결과에만 사용자 상태, Supabase 기본 세션과 메인 이동을 연결한다.

이번 구현 작업 목록에는 2단계의 실제 인증 연결을 포함하지 않는다.

## 검증 계획

- `/login`에서 Header가 페이지 내부에 중복 렌더링되지 않는지 확인한다.
- 초기 입력값, 기본 세션 유지 안내, 오류와 버튼 활성화 상태를 명세와 비교한다.
- `1320px`, `1024px`, `480px`에서 각 디자인의 주요 너비·간격·로고·버튼 크기를 확인한다.
- 이메일 필수·형식 및 비밀번호 필수 오류의 표시와 해제를 확인한다.
- 카카오·구글 버튼에 지정된 SVG가 올바르게 대응되는지 확인한다.
- Input의 테두리·radius·그림자·여백과 `person`, `lock` 아이콘이 Figma 값과 일치하는지 확인한다.
- 로그인 Input과 버튼이 공통 SCSS mixin을 사용하고 별도 공통 React 컴포넌트를 만들지 않았는지 확인한다.
- 회원가입 링크가 `/signup`을 가리키는지 확인한다.
- 실제 인증, 세션 저장, OAuth 이동과 가짜 성공 처리가 포함되지 않았는지 확인한다.
- 개발 서버에서 수동 확인 후 `npm run lint`를 실행한다. Production build는 페이지 통합 또는 배포 전 검증에서 수행한다.
