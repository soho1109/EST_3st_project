- `/login`에서는 공통 Header가 접힌 상태로 시작한다.
- 비로그인 사용자의 기본 화면에는 비로그인·접힘 Header를 적용한다.
- 로그인 사용자의 접근 제한 안내 중에는 로그인·접힘 Header를 적용한다.
- Header는 사이트 공통 영역에서 한 번 제공되며 로그인 페이지가 별도로 중복 제공하지 않는다.
- Header의 펼침·접힘, 사용자 상태, 페이지 이동 중 상태 유지, 로고와 메뉴 동작은 공통 Header 명세와 담당 작업의 결과를 따른다.
- `/login` 최초 진입 시 Header 접힘 처리는 공통 Header 작업의 의존 사항이며 로그인 페이지 범위에서 Header 또는 사이트 공통 영역을 변경하지 않는다.

## 작업 범위와 책임

- 로그인 페이지 범위는 `/login`의 화면, 입력 상태, 입력 검증, 요청 상태 표현, 폼 오류 안내와 공통 모달 호출 조건이다.
- 로그인 페이지 전용 화면과 스타일은 각각 `src/app/(site)/login/page.js`, `src/app/(site)/login/page.module.scss`에 대응한다.
- 공통 Header와 이를 제공하는 사이트 공통 영역은 로그인 페이지 작업에서 수정하지 않는다.
- 로그인 요청 중 진행 상태는 완성된 공통 Loading을 재사용하며 로그인 페이지가 별도의 전체 화면 로딩 UI를 만들지 않는다.
- 로그인 요청의 시작과 종료를 아는 로그인 페이지가 Boolean `isLoading` 상태를 소유하고 Loading의 표시 여부를 결정한다.
- UI 우선 단계에서는 입력과 화면 상태를 검증하되 실제 인증 성공, 사용자 판정과 시스템 오류가 없으므로 CommonModal 상태나 표시 경계를 미리 만들지 않는다.
- 실제 이메일 인증, 소셜 인증, 세션 유지와 로그인 사용자 정보 갱신은 인증 계약이 확정된 후 연결하는 후속 범위다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 이메일과 비밀번호로 로그인 (우선순위: P1)

비로그인 사용자는 가입한 이메일과 비밀번호를 입력해 본인 계정으로 로그인하고 메인 화면으로 이동한다.

**우선순위 이유**: 기존 계정 사용자가 서비스에 접근하는 가장 기본적인 인증 흐름이다.

**독립 검증**: 비어 있는 로그인 화면에서 유효한 계정 정보를 입력하고 로그인을 완료해 메인 화면과 로그인 상태 Header를 확인한다.

**인수 시나리오**:

1. **상황** 비로그인 사용자가 로그인 화면에 처음 진입했을 때, **동작** 화면을 확인하면, **결과** 비로그인·접힘 Header, 로고와 소개 문구, 비어 있는 이메일·비밀번호 입력란, 로그인 상태 유지 안내, 비활성화된 로그인 버튼과 간편 로그인 버튼이 표시되고 오류와 요청 중 상태는 표시되지 않는다.
2. **상황** 유효한 계정의 이메일과 비밀번호가 입력되어 있을 때, **동작** 사용자가 로그인 버튼을 선택하면, **결과** 이메일 로그인이 한 번 요청된다.
3. **상황** 이메일 로그인이 성공했을 때, **동작** 로그인 상태 갱신이 완료되면, **결과** Header가 로그인 상태로 변경되고 메인 화면(`/`)으로 이동한다.
4. **상황** 이메일 또는 비밀번호가 비어 있거나 이메일 형식이 올바르지 않을 때, **동작** 사용자가 입력란에서 벗어나면, **결과** 이메일·비밀번호·로그인 버튼 영역 하단의 고정된 오류 공간에 우선순위가 가장 높은 오류 문구 하나가 표시되고 로그인 버튼은 비활성화된다.
5. **상황** 오류가 표시된 입력값을 사용자가 수정할 때, **동작** 입력 상태가 변경되면, **결과** 현재 우선순위에 맞는 오류 문구로 즉시 갱신되고 모든 입력값이 유효하면 문구가 제거되며 로그인 버튼이 활성화된다.
6. **상황** 이메일 로그인 요청이 시작됐을 때, **동작** 로그인 페이지가 `isLoading`을 활성화하면, **결과** 공통 Loading이 화면 전체에 한 번 표시되고 모든 로그인 동작이 비활성화되어 중복 또는 교차 요청이 차단된다.
7. **상황** 이메일 로그인이 실패했을 때, **동작** 실패 결과가 반환되면, **결과** 이메일은 유지되고 비밀번호는 초기화되며 폼 근처에 “이메일 또는 비밀번호를 확인해 주세요.”가 표시된다.
8. **상황** 이메일 로그인을 완료했을 때, **동작** 이후 서비스를 다시 이용하면, **결과** Supabase의 기본 세션 갱신 정책에 따라 로그인 상태가 복구된다.
9. **상황** 이메일 로그인 요청이 성공하거나 실패했을 때, **동작** 요청 처리가 끝나면, **결과** `isLoading`이 해제되고 공통 Loading이 제거된다.

### 사용자 스토리 2 - 카카오 또는 구글로 간편 로그인 (우선순위: P2)

비로그인 사용자는 이메일과 비밀번호를 직접 입력하지 않고 카카오 또는 구글 계정을 선택해 로그인한다.

**우선순위 이유**: 외부 계정을 보유한 사용자가 더 적은 입력으로 서비스에 접근할 수 있게 한다.

**독립 검증**: 카카오와 구글 버튼을 각각 선택해 해당 로그인 과정으로 이동하고, 성공 후 메인 화면과 로그인 상태 Header를 확인한다.

**인수 시나리오**:

1. **상황** 비로그인 사용자가 로그인 화면에 있을 때, **동작** 카카오 로그인 버튼을 선택하면, **결과** 카카오 계정 로그인 과정으로 이동한다.
2. **상황** 비로그인 사용자가 로그인 화면에 있을 때, **동작** 구글 로그인 버튼을 선택하면, **결과** 구글 계정 로그인 과정으로 이동한다.
3. **상황** 카카오 또는 구글 로그인이 성공했을 때, **동작** 서비스로 돌아오면, **결과** 로그인 상태가 갱신되고 메인 화면(`/`)으로 이동한다.
4. **상황** 사용자가 카카오 또는 구글 인증을 취소했을 때, **동작** 서비스로 돌아오면, **결과** 별도 오류 안내 없이 로그인 화면이 표시되고 사용자는 다시 시도할 수 있다.
5. **상황** 카카오 또는 구글 인증이 실패했을 때, **동작** 서비스로 돌아오면, **결과** 로그인 폼 근처에 간편 로그인 실패 안내가 표시되고 사용자는 다시 시도할 수 있다.

### 사용자 스토리 3 - 접근 제한과 보조 로그인 경로 (우선순위: P3)

로그인 사용자는 로그인 화면에 중복 접근하지 않으며, 비로그인 사용자는 회원가입 경로를 이용할 수 있다.

**우선순위 이유**: 잘못된 접근을 정리하고 비밀번호 로그인이 어려운 사용자에게 다음 행동을 제공한다.

**독립 검증**: 로그인 상태의 접근 제한과 회원가입 이동을 각각 확인한다.

**인수 시나리오**:

1. **상황** 로그인 사용자가 `/login`에 접근했을 때, **동작** 접근 상태가 확인되면, **결과** 공통 모달의 `alreadyLoggedIn` 안내가 표시되고 3초 후 메인 화면(`/`)으로 이동한다.
2. **상황** 비로그인 사용자가 회원가입 안내를 보고 있을 때, **동작** 회원가입 링크를 선택하면, **결과** 회원가입 화면(`/signup`)으로 이동한다.
3. **상황** `alreadyLoggedIn` 안내가 표시된 상태에서, **동작** 사용자가 닫기 아이콘을 선택하면, **결과** 예약된 자동 이동이 취소되고 즉시 메인 화면(`/`)으로 한 번 이동한다.

### 예외 상황

- 입력 검증 오류는 각 입력란 아래에 따로 표시하지 않고 이메일·비밀번호·로그인 버튼 영역 하단의 단일 오류 공간에 한 문구만 표시한다.
- 이메일이 비어 있으면 비밀번호 상태와 관계없이 “이메일을 입력해 주세요.”를 가장 먼저 표시한다.
- 이메일 값이 있지만 형식이 올바르지 않으면 “올바른 이메일 형식을 입력해 주세요.”를 표시한다.
- 이메일이 유효하고 비밀번호만 비어 있으면 “비밀번호를 입력해 주세요.”를 표시하며, 로그인에서는 회원가입용 비밀번호 조합 규칙을 다시 검사하지 않는다.
- 입력 검증 오류는 사용자가 입력란에서 벗어난 뒤 표시하고, 이후 입력 상태가 바뀌면 이메일 빈 값, 이메일 형식, 비밀번호 빈 값 순서로 즉시 다시 판단한다.
- 단일 오류 공간은 오류가 없을 때도 높이를 유지하여 문구 표시와 제거로 로그인 화면의 다른 요소가 이동하지 않게 한다.
- 로그인 버튼은 이메일과 비밀번호의 필수·형식 검증이 모두 통과한 경우에만 활성화한다.
- 이메일 로그인 요청 중에는 `isLoading`으로 공통 Loading을 표시하고 모든 로그인 입력과 버튼 및 인증 동작을 비활성화한다.
- 로그인 이벤트 요청에는 Suspense 대체 화면이나 경로 단위 자동 로딩을 함께 사용하지 않으며, 공통 Loading을 한 번만 표시한다.
- 로그인 요청은 성공과 실패 여부에 관계없이 종료 시 로딩 상태를 해제한다.
- 이메일 또는 비밀번호 불일치로 로그인이 실패하면 응답 상태가 401이어도 공통 오류 모달을 사용하지 않고, 이메일은 유지하고 비밀번호는 초기화한 뒤 로그인 폼 근처에 “이메일 또는 비밀번호를 확인해 주세요.”를 표시한다.
- 서버·서비스 장애 또는 네트워크 장애는 공통 모달의 `error` 모드로 안내하며, 원본 오류 메시지나 민감한 내부 정보는 표시하지 않는다.
- 로그인 페이지의 비밀번호 입력란은 표시·숨김 기능 없이 항상 마스킹한다.
- 로그인 세션은 별도의 사용자 선택 없이 Supabase의 기본 세션 갱신 정책을 사용한다.
- 로그인 폼에는 `로그아웃 전까지 로그인 상태가 유지됩니다.` 안내를 표시한다.
- 카카오 또는 구글 인증을 취소하면 안내 없이 로그인 화면으로 돌아오고, 실패하면 폼 근처에 실패 안내를 표시하며 두 경우 모두 다시 시도할 수 있다.
- 매직 링크 로그인은 이번 기능 범위에서 제외하며 UI와 동작은 추후 별도 명세에서 결정한다.
- 로그인한 사용자의 `alreadyLoggedIn` 안내가 표시되는 동안에는 로그인·접힘 Header를 표시한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 `/login`에서 비로그인 사용자가 로그인할 수 있는 화면을 제공해야 한다.
- **FR-002**: 로그인 사용자가 `/login`에 접근하면 공통 모달의 `alreadyLoggedIn` 모드로 “이미 로그인하셨습니다. 메인페이지로 이동합니다.”를 안내하고 표시 후 3초 뒤 메인 화면(`/`)으로 이동시켜야 한다.
- **FR-003**: 로그인 화면은 공통 Header를 접힌 상태로 표시해야 한다.
- **FR-004**: 최초 진입 시 이메일과 비밀번호는 비어 있고 로그인 상태 유지 안내가 표시되며 입력 오류와 요청 중 상태는 표시되지 않아야 한다.
- **FR-005**: 화면은 큰 로고와 서비스 소개 문구, 이메일 로그인 폼, 카카오·구글 로그인 버튼, 회원가입 안내와 링크를 제공해야 한다.
- **FR-006**: 이메일은 필수이며 올바른 이메일 형식이어야 한다.
- **FR-007**: 비밀번호는 필수이고 기본적으로 마스킹되어야 하며, 로그인 단계에서는 회원가입용 조합 규칙을 검사하지 않아야 한다.
- **FR-008**: 이메일과 비밀번호 입력 오류는 사용자가 입력란에서 벗어난 뒤 이메일·비밀번호·로그인 버튼 영역 하단의 단일 오류 공간에 한 문구만 표시하고, 사용자가 값을 수정하면 현재 우선순위에 맞게 즉시 갱신하거나 해제해야 한다.
- **FR-009**: 로그인 버튼은 이메일과 비밀번호의 필수·형식 검증이 모두 통과한 경우에만 활성화해야 한다.
- **FR-010**: 유효하지 않은 입력 상태에서는 로그인 버튼을 비활성화하고 이메일 로그인 요청을 시작하지 않아야 한다.
- **FR-011**: 유효한 이메일과 비밀번호로 로그인 버튼을 선택하면 시스템은 이메일 로그인을 한 번 요청해야 한다.
- **FR-012**: 이메일 로그인 요청은 사용자가 입력한 이메일과 비밀번호를 사용해야 한다.
- **FR-013**: 이메일 로그인 요청 중에는 로그인 페이지가 소유한 Boolean `isLoading` 상태로 공통 Loading을 화면 전체에 한 번 표시하고 모든 로그인 입력, 버튼 및 인증 동작을 비활성화하여 중복 또는 교차 요청을 차단해야 한다.
- **FR-014**: 이메일 로그인이 성공하면 사용자 로그인 상태와 Header를 갱신한 뒤 메인 화면(`/`)으로 이동해야 한다.
- **FR-015**: 이메일 로그인이 실패하면 이메일과 비밀번호 중 어느 값이 잘못됐는지 구분하지 않는 공통 오류를 표시해야 한다.
- **FR-016**: 이메일 로그인 실패 시 이메일 입력값은 유지하고 비밀번호는 초기화한 뒤 로그인 폼 근처에 “이메일 또는 비밀번호를 확인해 주세요.”를 표시해야 한다.
- **FR-017**: 비밀번호 입력란은 표시·숨김 기능을 제공하지 않고 항상 마스킹된 상태를 유지해야 한다.
- **FR-018**: 로그인 폼은 `로그아웃 전까지 로그인 상태가 유지됩니다.` 안내를 작고 연한 글자로 표시해야 한다.
- **FR-019**: 로그인 성공 후 세션은 별도의 사용자 선택 없이 Supabase의 기본 세션 갱신 정책을 사용해야 한다.
- **FR-020**: 로그인 폼은 세션 저장 방식을 선택하는 체크박스를 제공하지 않아야 한다.
- **FR-021**: 카카오 로그인 버튼을 선택하면 카카오 계정 로그인 과정으로 이동해야 한다.
- **FR-022**: 구글 로그인 버튼을 선택하면 구글 계정 로그인 과정으로 이동해야 한다.
- **FR-023**: 카카오 또는 구글 로그인이 성공하면 사용자 로그인 상태와 Header를 갱신한 뒤 메인 화면(`/`)으로 이동해야 한다.
- **FR-024**: 이메일·카카오·구글 로그인에 별도의 로그인 상태 유지 선택값을 적용하지 않아야 한다.
- **FR-025**: 카카오 또는 구글 로그인을 취소하면 별도 오류 안내 없이 로그인 화면으로 돌아오고 사용자가 다시 시도할 수 있어야 한다.
- **FR-026**: 카카오 또는 구글 로그인이 실패하면 로그인 화면으로 돌아와 폼 근처에 간편 로그인 실패 안내를 표시하고 다시 시도할 수 있어야 한다.
- **FR-027**: 회원가입 안내의 회원가입 링크는 회원가입 화면(`/signup`)으로 연결되어야 한다.
- **FR-028**: 매직 링크 로그인은 이번 기능 범위에 포함하지 않아야 한다.
- **FR-029**: 화면의 배치, 크기, 색상, 타이포그래피와 기본 외형은 연결된 로그인 페이지 디자인을 따라야 하며, 확정된 문구와 동작은 이 명세를 우선해야 한다.
- **FR-030**: 로그인 화면의 Header는 공통 Header 명세를 따라야 한다.
- **FR-031**: 비로그인 사용자의 로그인 화면은 비로그인·접힘 Header를 표시하고 회색 꿀벌 이미지로 사용자 상태를 구분해야 한다.
- **FR-032**: 로그인 사용자의 접근 제한 알림 중에는 로그인·접힘 Header를 표시하고 로그인 상태용 꿀벌 이미지로 사용자 상태를 구분해야 한다.
- **FR-033**: `alreadyLoggedIn` 안내의 닫기 아이콘을 선택하면 남은 자동 이동을 취소하고 즉시 메인 화면(`/`)으로 한 번 이동해야 한다.
- **FR-034**: 로그인 페이지는 공통 Header를 중복 표시해서는 안 되며 사이트 공통 영역에서 제공되는 Header를 사용해야 한다.
- **FR-035**: 이메일 또는 비밀번호 불일치와 입력 검증 오류는 로그인 폼 내부에 표시하고 공통 모달의 `error` 모드로 처리해서는 안 된다.
- **FR-036**: 이메일 또는 비밀번호 불일치가 401 상태로 전달되더라도 자격 정보 실패로 분류하여 이메일을 유지하고 비밀번호를 초기화한 뒤 동일한 폼 오류 문구를 표시해야 한다.
- **FR-037**: 서버·서비스 장애와 네트워크 장애는 공통 모달의 `error` 모드로 안내하고 공통 모달에 정의된 상태별 문구와 이동 규칙을 따라야 한다.
- **FR-038**: 로그인 페이지는 서버의 원본 오류 메시지, 내부 경로, 스택 또는 민감 정보를 사용자에게 표시해서는 안 된다.
- **FR-039**: UI 우선 검증 단계는 입력, 검증과 요청 중 표시 경계를 확인할 수 있어야 하며 실제 인증·세션 저장을 성공한 것처럼 처리하거나 CommonModal용 임시 상태를 만들어서는 안 된다.
- **FR-040**: 실제 인증, 소셜 인증과 사용자 상태 갱신은 인증 계약에 따라 연결해야 한다.
- **FR-041**: 이메일 로그인 요청은 성공과 실패 여부에 관계없이 처리가 종료되면 `isLoading`을 해제하고 공통 Loading을 제거해야 한다.
- **FR-042**: 로그인 이벤트 요청에는 Suspense 대체 화면을 사용해서는 안 된다.
- **FR-043**: 동일한 로그인 요청에 `isLoading` 기반 공통 Loading과 Suspense 대체 화면을 중복 적용해서는 안 된다.
- **FR-044**: 로그인 경로에 경로 단위 자동 로딩 파일을 생성하거나 사용해서는 안 된다.
- **FR-045**: 로그인 페이지는 공통 Loading의 화면과 동작을 재사용해야 하며 별도의 전체 화면 로딩 UI를 중복 생성해서는 안 된다.
- **FR-046**: 카카오 로그인 버튼은 `public/images/kakao-icon.svg`, 구글 로그인 버튼은 `public/images/google-icon.svg`를 각 제공자 식별 아이콘으로 표시해야 한다.
- **FR-047**: 로그인 입력란은 디자인에 정의된 테두리, 모서리 반경, 그림자와 내부 여백을 적용해야 한다.
- **FR-048**: 이메일과 비밀번호 입력란은 각각 Material Symbols의 `person`, `lock` 아이콘을 표시해야 한다.
- **FR-049**: 입력란과 버튼의 공통 외형은 프로젝트 공통 SCSS mixin으로 제공하되 React 공통 Input 또는 Button 컴포넌트를 새로 만들지 않아야 한다.
- **FR-050**: 공통 버튼 mixin은 페이지별 배경색과 너비를 지정할 수 있어야 한다.
- **FR-051**: 입력 검증 오류 문구는 이메일 빈 값의 “이메일을 입력해 주세요.”, 이메일 형식 오류의 “올바른 이메일 형식을 입력해 주세요.”, 이메일이 유효한 상태의 비밀번호 빈 값인 “비밀번호를 입력해 주세요.” 순서로 우선 적용해야 한다.
- **FR-052**: 단일 오류 공간은 오류 문구가 없을 때도 높이를 유지하여 오류 표시 전후에 로그인 화면의 다른 요소가 이동하지 않게 해야 한다.

### 핵심 엔티티 *(데이터를 다루는 경우에만 작성)*

- **로그인 자격 정보**: 사용자가 입력한 이메일과 비밀번호이며 이메일 로그인 요청에 사용된다.
- **로그인 세션**: 로그인 성공 후 Supabase의 기본 세션 갱신 정책으로 유지되는 인증 상태다.
- **로그인 처리 상태**: 요청 전, 요청 중, 성공, 실패와 실패 안내 상태를 나타낸다.
- **소셜 로그인 제공자**: 카카오 또는 구글 중 사용자가 선택한 외부 계정 로그인 경로다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 유효한 계정 정보를 가진 비로그인 사용자는 로그인 화면 진입 후 2분 이내에 이메일 로그인을 완료할 수 있다.
- **SC-002**: 비어 있거나 형식이 잘못된 입력으로 이메일 로그인 요청이 발생하는 사례가 없어야 한다.
- **SC-003**: 이메일 로그인 성공 시 사용자는 한 번의 로그인 요청으로 메인 화면과 로그인 상태 Header에 도달해야 한다.
- **SC-004**: 잘못된 이메일 또는 비밀번호로 실패한 모든 검증 사례에서 어느 값이 틀렸는지를 노출하지 않는 동일한 실패 안내를 확인할 수 있어야 한다.
- **SC-005**: 카카오와 구글 로그인 성공 시나리오 각각에서 사용자가 메인 화면과 로그인 상태 Header에 도달해야 한다.
- **SC-006**: 로그인 사용자는 `/login` 접근 시 `alreadyLoggedIn` 안내가 표시되고, 3초를 기다리거나 닫기 아이콘을 한 번 선택하여 메인 화면에 한 번 도달해야 한다.
- **SC-007**: 회원가입 링크를 한 번 선택해 회원가입 화면에 도달할 수 있어야 한다.
- **SC-008**: 로그인 요청 중 반복 선택으로 두 건 이상의 이메일 로그인 요청이 발생하는 사례가 없어야 한다.
- **SC-009**: 기준 디자인과 비교했을 때 명세에서 승인한 차이를 제외한 주요 화면 요소가 누락되지 않아야 한다.
- **SC-010**: 비로그인 접근과 로그인 접근 제한 상황 모두에서 올바른 접힘 Header와 사용자 상태 이미지가 표시되어야 한다.
- **SC-011**: 로그인 폼에 세션 선택 체크박스 없이 로그인 상태 유지 안내가 표시되고, 로그인 성공 후 Supabase 기본 세션 정책이 적용되어야 한다.
- **SC-012**: 카카오·구글 인증 취소 시 오류 없이 로그인 화면으로 돌아오고, 인증 실패 시 폼 근처에 오류가 표시되며 두 경우 모두 다시 시도할 수 있어야 한다.
- **SC-013**: 이메일 또는 비밀번호 불일치 검증 사례의 100%에서 공통 오류 모달이 열리지 않고 지정된 폼 오류가 표시되어야 한다.
- **SC-014**: 서버·서비스 및 네트워크 장애 검증 사례의 100%에서 내부 오류 원문 없이 공통 오류 안내와 지정된 후속 이동이 제공되어야 한다.
- **SC-015**: 로그인 페이지에서 공통 Header가 두 개 이상 동시에 표시되는 사례는 0건이어야 한다.
- **SC-016**: 이메일 로그인 요청의 성공과 실패 검증 사례 모두에서 요청 종료 후 공통 Loading이 제거되고 로그인 화면의 상호작용이 복구되어야 한다.
- **SC-017**: 하나의 이메일 로그인 요청에서 전체 화면 Loading이 두 개 이상 겹쳐 표시되는 사례는 0건이어야 한다.
- **SC-018**: 이메일 로그인 요청 중 뒤쪽 로그인 입력과 인증 버튼으로 전달되는 사용자 상호작용은 0건이어야 한다.
- **SC-019**: 카카오와 구글 로그인 버튼의 모든 검증 사례에서 각 제공자에 지정된 아이콘이 서로 바뀌거나 누락되지 않아야 한다.
- **SC-020**: 로그인 입력란의 테두리, 모서리 반경, 그림자, 내부 여백과 Material Symbols가 기준 디자인과 일치해야 한다.
- **SC-021**: 로그인 페이지가 Input 또는 Button 역할의 새로운 공통 React 컴포넌트를 생성하는 사례는 0건이어야 한다.
- **SC-022**: 이메일·비밀번호 검증 오류의 모든 조합에서 단일 오류 공간에는 지정된 우선순위의 문구 하나만 표시되어야 한다.
- **SC-023**: 입력 검증 오류 문구가 표시되거나 제거될 때 로그인 화면의 입력, 버튼과 보조 요소 위치가 이동하지 않아야 한다.

## 가정

- 이메일과 비밀번호, 카카오, 구글 로그인을 처리하고 로그인 사용자 정보를 제공하는 인증 서비스가 별도 제공된다.
- 인증 및 세션 유지의 구체적인 구현 구조는 이 명세에서 결정하지 않는다.
- 실패 응답은 사용자에게 계정 존재 여부나 어떤 입력값이 잘못됐는지 노출하지 않는 공통 안내로 변환할 수 있다.
- 로그인 자격 정보 실패와 시스템 장애를 구분할 수 있는 인증 결과 계약이 후속 연동 단계에서 제공된다.
- Header의 구체적인 동작과 외형은 공통 Header 명세를 따르며 `/login` 최초 접힘 처리는 Header 담당 작업에서 제공된다. 로그인 페이지 작업은 Header와 사이트 공통 영역을 변경하지 않는다.
- 공통 모달의 `alreadyLoggedIn`과 `error` 모드의 문구, 타이머, 닫기 및 이동 규칙은 공통 모달 계약을 따른다.
- 공통 Loading의 디자인, 안내 문구, 상호작용 차단과 접근성 표현은 공통 Loading 명세와 UI 계약을 따른다.
- 로그인 이벤트 요청은 호출 측 `isLoading`으로 제어하며 비동기 콘텐츠 렌더링용 Suspense 정책과 구분할 수 있다.
- `public/images/kakao-icon.svg`와 `public/images/google-icon.svg`는 현재 파일명과 위치를 유지한다.
- 공통 Input과 버튼 외형은 기존 `src/styles/abstracts/_mixins.scss`에 추가되는 mixin을 사용하고 페이지별 차이는 인자로 전달하거나 전용 스타일에서 확장한다.
- 매직 링크 로그인은 후속 명세에서 범위, UI와 완료 안내를 결정한다.
