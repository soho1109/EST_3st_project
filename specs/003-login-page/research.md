# 조사 결과: 로그인 페이지

## 로그인 페이지의 Client Component 경계

**결정**: 이메일·비밀번호 입력, 입력란 이탈, 폼 오류, `isLoading`과 모달 공개 상태를 소유하는 `page.js`만 Client Component로 구성한다.

**근거**: 사용자 이벤트와 상태가 필요한 컴포넌트에는 클라이언트 경계가 필요하다. 상위 사이트 레이아웃과 Header는 이번 작업 범위가 아니므로 변경하지 않는다.

**대안**: 페이지 전체를 서버 컴포넌트로 유지하고 별도 폼 컴포넌트를 추가하는 방법은 새 파일과 구조를 요구하므로 승인된 두 파일 범위를 벗어나 제외한다.

**참고**: [Next.js `use client`](https://nextjs.org/docs/app/api-reference/directives/use-client)

## UI 우선 단계와 인증 연동 경계

**결정**: UI 우선 단계는 입력·검증·버튼 상태·공통 컴포넌트 배치를 구현하되 가짜 성공 응답, 사용자 상태, 세션 저장과 메인 이동을 만들지 않는다. 실제 요청 생명주기와 결과 분기는 인증 계약 확정 후 같은 이벤트 경계에 연결한다.

**근거**: 실제 인증 구조를 임의로 정하지 않으면서도 화면과 상태 책임을 먼저 완성할 수 있다. 테스트용 성공을 실제 로그인처럼 저장하면 이후 인증 계약과 충돌할 수 있다.

**대안**: 지연 Promise로 성공을 흉내 내는 방식은 Loading 시연에는 편하지만 가짜 인증 흐름이 제품 코드에 남을 수 있어 제외한다.

## 로그인 요청의 Loading 제어

**결정**: 실제 인증 연결 후 이벤트 처리 영역이 Boolean `isLoading`을 소유하고 요청 시작 직전에 활성화하며 종료 시 항상 해제한다. 로그인 이벤트 요청에는 Suspense fallback과 `loading.js`를 사용하지 않는다.

**근거**: 이벤트 핸들러에서 시작한 요청은 명시적 상태로 생명주기와 중복 제출을 제어하는 것이 공통 Loading 계약과 일치한다.

**대안**: Suspense fallback은 렌더 중 실제로 대기하는 콘텐츠에 적합하지만 로그인 버튼으로 시작한 요청을 자동 관리하지 않으므로 제외한다.

**참고**: [React Suspense](https://react.dev/reference/react/Suspense), [React useState](https://react.dev/reference/react/useState)

## 오류 분류

**결정**: 입력 검증과 자격 정보 불일치는 폼 내부 오류로, 서버·서비스·네트워크 장애는 `CommonModal`의 `error` 모드로 구분한다. 자격 정보 불일치가 401이어도 폼 오류가 우선한다.

**근거**: 사용자가 입력을 수정해 해결할 수 있는 문제와 시스템 문제를 구분해야 불필요한 페이지 이동을 막을 수 있다. CommonModal의 401 기본 동작은 로그인 페이지로 이동하므로 자격 정보 실패에 사용하면 같은 화면에서 수정하는 흐름과 맞지 않는다.

**대안**: 모든 비성공 응답을 공통 오류 모달로 처리하면 구현은 단순하지만 사용자가 비밀번호를 바로 다시 입력하기 어렵고 기존 명세와 충돌한다.

## 내부 이동

**결정**: 회원가입처럼 목적지가 고정된 내부 경로는 `Link`를 사용한다. 인증 결과에 따른 메인 이동은 실제 인증 연동 단계에서 조건부 이동으로 처리한다.

**근거**: 고정 내부 경로에는 선언적 이동이 적합하고, 인증 성공 여부에 따라 결정되는 이동은 요청 결과가 확정된 뒤에만 실행되어야 한다.

**대안**: 회원가입 이동에도 프로그램 방식 이동을 사용하면 불필요한 이벤트 로직이 생기므로 제외한다.

**참고**: [Next.js Link](https://nextjs.org/docs/app/api-reference/components/link)

## 소셜 로그인 아이콘

**결정**: 카카오는 `/images/kakao-icon.svg`, 구글은 `/images/google-icon.svg`를 사용하고 버튼 텍스트로 제공자 이름을 함께 표시한다.

**근거**: 지정된 로컬 자산을 재사용하며 아이콘만으로 의미를 전달하지 않아 시각적 식별과 접근 가능한 이름을 함께 제공할 수 있다.

**대안**: 외부 이미지 URL이나 아이콘 패키지는 새 의존성 또는 외부 자산 관리가 필요하므로 제외한다.

**참고**: [Next.js Image](https://nextjs.org/docs/app/api-reference/components/image)

## Input과 버튼의 공통화 범위

**결정**: 로그인과 회원가입에서 반복되는 Input 테두리·그림자·모서리와 버튼 정렬·타이포그래피·모서리는 공통 SCSS mixin으로 제공한다. 공통 Input 또는 Button React 컴포넌트는 만들지 않는다. 버튼 mixin은 배경색과 너비를 인자로 받는다.

**근거**: 현재 공통점은 표현 스타일이며 페이지별 내용·아이콘·동작·배치가 다르다. SCSS mixin은 중복 스타일을 줄이면서 컴포넌트 props와 책임을 불필요하게 늘리지 않는다.

**대안**: 공통 React 컴포넌트는 입력 동작과 props 계약까지 공통일 때 적합하지만 현재 요구 범위를 넘어 제외한다. 각 페이지에 스타일을 복사하는 방법은 동일 디자인의 변경 누락 위험이 있어 제외한다.

## 반응형 디자인과 충돌 해결

**결정**: `1320px`, `1024px`, `480px` Figma 노드에서 확인한 구조와 크기 변화는 화면별로 적용한다. 배경, Input 그림자, placeholder와 기능 문구는 데스크톱 기준으로 모든 화면에 통일한다.

**근거**: 태블릿·모바일 노드는 데스크톱과 Input 그림자·placeholder 색상 및 `아이디`·`아이디저장` 문구가 달랐지만, 기능 명세는 이메일 로그인과 동일한 기본 세션 유지 안내를 요구한다. 화면 크기에 따라 기능 의미가 달라져서는 안 되며 사용자가 데스크톱 시각 기준 통일을 확정했다.

**대안**: 각 Figma 노드의 모든 값을 그대로 적용하면 반응형에 따라 입력 의미가 바뀌므로 제외한다. 모든 크기와 배치를 데스크톱처럼 고정하는 방법은 작은 화면 디자인을 반영하지 못하므로 제외한다.

## 로그인 세션 유지 정책

**결정**: 세션 저장 방식 선택 UI와 Boolean 상태는 두지 않는다. 로그인 성공 후 Supabase의 기본 세션 갱신 정책을 사용하고 로그인 폼에는 이를 알리는 안내 문구를 표시한다.

**근거**: 현재 프로젝트의 `@supabase/ssr` 구조는 쿠키 기반 세션과 토큰 갱신을 사용하므로, 로그인별 저장 방식 분기를 추가하지 않고 기본 세션 수명주기를 유지한다.

**대안**: UI 단계에서 브라우저 저장소를 직접 선택하거나 토큰을 저장하는 방식은 인증 구조를 페이지에 분산시키므로 제외한다. Supabase Pro의 세션 수명 제한 기능은 프로젝트 사용 범위가 아니므로 조사·계획 대상에서 제외한다.

## 입력 아이콘

**결정**: Figma에서 내보낸 임시 SVG URL 대신 프로젝트에 이미 연결된 Material Symbols를 사용한다. 이메일은 `person`, 비밀번호는 `lock` glyph를 사용한다.

**근거**: 사용자가 Material icon 사용을 확정했고 프로젝트 root layout에 Material Symbols Outlined가 이미 연결되어 있다.

**대안**: Figma 임시 SVG는 만료되는 외부 자산이며 별도 로컬 아이콘 파일 추가가 필요하므로 제외한다.

## Header 소유권

**결정**: 로그인 페이지는 Header를 렌더링하지 않고 `src/app/(site)/layout.js`가 제공하는 기존 Header를 사용한다. `/login` 최초 접힘 처리는 Header 담당 작업에 의존한다.

**근거**: 로그인 페이지에서 Header를 다시 렌더링하면 중복 표시되고 팀원의 공통 Header 작업 범위를 침범한다.

**대안**: 로그인 페이지에서 Header props나 상태를 직접 제어하는 방법은 현재 계약과 팀 작업 경계를 변경하므로 제외한다.
